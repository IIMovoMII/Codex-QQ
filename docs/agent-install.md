# 智能体安装指南

这是执行入口，不是让用户逐条照抄的教程。用户给出 README 的“一句话安装”后，由你完成能够在本机完成的检查、构建、配置与验证；需要用户操作 QQ 平台或本机安全输入时，再给出当前这一步的简短提示。

先读 [README](../README.md)、[首次安装](install.md)和[使用手册](usage.md)。以当前源码和本机检查为准，可以调整命令、路径和依赖安装方式，不要照搬作者的环境，也不要扩展到账号切换、聊天修复或其他通讯平台。

## 交付目标

用户正常启动 Codex Desktop 后，手机 QQ 能列出并选中自己的本地对话；引用回执能发送任务，完成后能在 QQ 聊天中看见结果。助手是独立托盘应用，退出 Codex 不退出助手，退出助手不关闭 Codex。Windows 登录自启由用户选择，默认不开启。

当前实现是 Windows 源码版，不是跨平台安装器。可自动部署不等于免注册、免密钥或无需用户确认。QQ 机器人资格、沙箱成员和上线权限以平台当前实际要求为准，不替用户承诺一定开通。

## 1. 先检测，少问问题

只读核对下列信息，能读取的不要再问用户：

- 操作系统、当前用户、是否有可用的 Windows 桌面/Explorer。不要用管理员账户代替实际使用账户安装。
- Codex Desktop 是否安装、实际进程和 `CODEX_HOME`；配置能否解析、现有钩子与当前采用的命令解释器。仅读取需要的字段，不输出认证、完整配置或历史正文。
- Python 3.11+、对应的 `pythonw.exe`、Git、Go 1.25+、Windows .NET Framework 编译器是否可用。当前自动测试覆盖 Python 3.11 和 3.13；Python 运行部分无第三方包。
- 是否已有 Codex-QQ 源码、助手/网关进程、运行配置、绑定和自启项，路径是否一致。
- 当前版本的安装、构建参数；不要猜测未提供的安装命令。

按情况处理：

| 检测结果 | 下一步 |
| --- | --- |
| 全新 Windows 环境，依赖齐全 | 直接进入构建和绑定 |
| 缺少构建依赖 | 说明缺少什么，按用户授权从官方发行渠道安装；没有安装权限则给出准确的人工步骤 |
| 已有正式安装 | 检查并复用现有目录/绑定，按[更新说明](development.md#重新构建与更新)升级，不重跑首次配置 |
| 有 `setup-pending.json` | 这是未完成的绑定，先检查进度和配置身份，不删除后从头创建 |
| 运行目录不明、两份安装冲突或配置无法解析 | 保留现状，核实来源；不能靠清空配置“解决” |
| 非 Windows、无交互桌面，或尚无可用的 Codex Desktop | 明确当前缺口；不要用 Codex CLI 或另一台电脑冒充本次安装成功 |

仅询问真正影响实施的选择：已有机器人还是需要创建、平台里是否使用沙箱、是否希望登录自启，以及无法自行判定的现有安装归属。可采用合理默认目录并告知用户，不要一次发长问卷。

## 2. 获取源码并构建

选择当前用户可写、长期保留的目录。首次下载可用 README 的 `git clone`；没有 GitHub 账号也能下载公开源码，不要求用户为此提供 GitHub Token。有现有副本时先检查改动和远端，不覆盖用户修改。

查看所用提交对应的 GitHub 检查状态，优先使用已通过的提交。如果检查失败或网络不可达，分别说明，不把“下载成功”当成“构建通过”。记录本次使用的提交。

在仓库目录运行（没有 `py` 时使用已核实的 Python 绝对路径）：

```powershell
py -3 -X utf8 tools/prepare_gateway.py
py -3 -X utf8 tools/build_resident_app.py
py -3 -X utf8 -m unittest discover -s tests -q
py -3 -X utf8 tools/check_publication.py
```

确认产生配套网关、`bin/CodexQQ助手.exe` 和本机 `bin/app-runtime.json`。启动入口依赖源码目录和构建时选定的 Python，不是可随意移动的单文件应用。下载 ZIP 而非 Git 副本时，公开文件检查需要 Git 索引；不能伪称该检查通过。

网关必须使用本仓库的固定上游基线和配套补丁，不换成任意最新版 `cc-connect.exe`。**固定构建依赖不等于固定 Codex 安装版本**；后者仍按实际接口能力判断。

构建中断时先检查报错和残留。`prepare_gateway.py` 拒绝覆盖已有构建目录/程序是保护，不是需要删除整个项目的理由。仅在确认属于本次失败构建且不被运行实例引用后清理具体残留，或按开发说明在独立构建目录生成候选文件。更新运行中的网关前只退出助手，不终止 Codex。

## 3. 引导用户准备 QQ 机器人

若用户没有机器人，引导到 [QQ 开放平台](https://q.qq.com/) 创建自己的机器人并开通所需私聊/测试权限。用户自己完成登录、实名、验证码、平台条款等操作；你负责根据当前页面解释下一步，不索取个人 QQ 登录密码。

AppID 和 AppSecret 通过本机配置工具填写：

```powershell
py -3 -X utf8 tools/configure.py
```

使用沙箱则加 `--sandbox`。为用户提供能够实际输入的本机终端；密钥由 `getpass` 隐藏输入。没有交互输入能力时，让用户在普通 PowerShell 完成这一个步骤，再接续部署。

不要让用户把 AppSecret 发给智能体聊天、QQ 或 GitHub；不要放入命令参数、环境回显、截图或测试文件。不要读取整个生成配置到工具输出中。只检查必要字段、文件是否存在和解析是否成功。

默认运行配置在 `%LOCALAPPDATA%\CodexDesktopWeixin`，QQ 数据在 `%LOCALAPPDATA%\CodexCC`。历史目录名不表示启用微信。源码可以放别处；普通安装不要改运行数据根目录。仅给 `configure.py` 传 `--data-dir` 不会同步修改钩子、托盘和自启入口，确需定制时必须把整条路径链一起适配并验证。

## 4. 获取并确认用户自己的 QQ 身份

按首次安装文档启动**配置专用网关**，然后只提示用户这一件事：

> 在你自己的 QQ 中打开刚创建的机器人私聊，发送“绑定”，把它返回的 OpenID 填到电脑的绑定提示里。这不是 QQ 号码。

此阶段只连接独立的身份查询器，不连接 Codex。临时接收所有身份只用于查询各自的 OpenID，不能改成正式桥接并长期保留 `allow_from = "*"`，也不能把“第一个给机器人发消息的人”自动认作机主。

停止这次配置网关（前台按 `Ctrl+C`，或只停止自己创建并核实身份的进程），再运行：

```powershell
py -3 -X utf8 tools/configure.py --bind
```

用户输入自己的 OpenID，并输入 `yes` 确认允许该身份控制电脑。工具会将入站白名单和出站私聊设为同一个身份，生成正式配置。没有收到用户确认就停在这里，不替用户猜身份，也不重复索取密钥。

绑定失败时看具体原因：普通 QQ 号码不是 OpenID；配置变化会触发完整性保护；已有正式配置不能用此工具覆盖。保持现有文件，明确修复当前步骤，不通过删除正式绑定重试。

## 5. 启动独立助手，再安装钩子

先启动 `bin/CodexQQ助手.exe`，或用 `codex-watch.cmd app` 走同一个独立启动入口。等待托盘出现，检查 `runtime_mode` 为 `independent`、助手进程身份正确。本次新安装不使用旧 `start`/`monitor`/`ensure-runtime` 作为常驻入口，不直接启动 `pythonw ... --brokered` 绕过 Explorer。

**先开启助手，再安装钩子。** 独立运行标记由助手建立；否则首次安装的钩子可能触发旧跟随模式。这时未安装钩子或尚无新活动，部分连接不可用是预期情况。

核对实际 Codex 配置目录后执行 `codex-watch.cmd install-hooks`；自定义 `CODEX_HOME` 时给安装命令传正确的 `--codex-home`。只合并本应用钩子与 `[features] hooks = true`。安装器会保存本次恢复副本；不要额外反复备份整个 `.codex`。

写前检查配置有效性，写后确认其他钩子/配置项还在。不改 auth、provider、模型、权限默认值、安装包或聊天历史；不替用户信任未知钩子。命令解释器不是 PowerShell 时，先适配命令引用规则再安装，不猜测中文路径的转义。

如果你正运行在需要重启的 Codex 内，不要关闭自己或其他正在工作的窗口。保存无密钥的安装进度、源码路径、已完成验证和下一步，告诉用户正常重启后继续。用户在 Desktop 核对本项目 Python 路径及 `cli.py hook` 并信任后，再进行功能验收；不把等待信任写成部署完成。

如果 `CODEX_HOME` 只在智能体的临时环境中设置，还要核对从 Explorer/自启启动时能否得到同一路径。默认托盘自启只保存应用入口，不自动保存临时命令参数；定制安装必须验证重开后的路径一致性，不能仅让本次终端启动成功。

## 6. 验收：不要只看“运行成功”

运行 `codex-watch.cmd doctor`，按本机情况核对钩子启用、助手与网关真实进程、本地 API 就绪、独立运行模式。不能用一个旧 PID 或历史日志代替当前就绪证据。

Codex 有新的受信任活动后，引导用户做最短手机验收：

1. 发“帮助”，看到简短首页；发“对话”，看到标题和项目。
2. 引用列表回复序号，再引用选定回执发“设置”，核对目标、模型、档位与权限。
3. 征得用户同意后，用选定的测试对话发送一个无害任务；在 Desktop 确认是同一对话、同一正文，不对用户正在执行的业务任务做实验。
4. 等完成后，确认 QQ **聊天页面**里能看到正文，不只是一条手机系统通知。

本地 API 的 `ready` 或平台返回消息编号都不能证明第 4 步通过。发送结果未知时，不为了验收重复发送控制指令。没有手机反馈、还未信任钩子或接口不兼容，就准确记录待验收/阻塞位置，不声称全链路成功。

可以另外说明“退出 Codex 后助手仍在、重新打开后可继续使用”，但不为此主动关闭用户的活动 Codex。自启仅在用户选择后启用并核实对应当前目录；默认关闭。

## 7. 失败处理与交付

优先按[常见问题](troubleshooting.md)定位一次明确原因，再修对应层。新接口不兼容时保留拒绝执行，不解除身份/目标校验，不改历史数据库，不把命令悄悄发给独立 CLI Agent。离线期间的新控制消息作废，不补执行。

撤销本次安装时只停止本应用拥有的进程，保留现有 QQ 绑定/队列；钩子用 `uninstall-hooks` 仅移除本程序定义。若要恢复安装前的配置，只恢复本次改动并核对其间是否有用户更新，不直接拿旧整文件覆盖。删除源码或运行数据、自启改动等清理必须与用户请求范围一致，不动 Codex 本身。

交付给用户只写重要内容：安装目录、如何开启/退出、是否自启、QQ 先发什么、已验证到哪一步、还需什么人工动作。需要跨重启接续时保存这些内容，但不保存密钥或完整诊断日志到仓库。不要把编译日志和内部实现当作用户操作手册。
